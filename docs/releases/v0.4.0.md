# wiretap v0.4.0

This release makes search cover your whole local history, closes out sessions
left behind by a crash, and fixes relay webhooks being rejected under concurrent
load.

## Search the whole history, not just the newest page

Traffic and webhook filtering now runs in SQLite instead of over the rows the
dashboard happens to be holding. Previously the lists held the newest 100 rows
and filtered those, so anything older was unreachable no matter how exactly it
matched — a busy machine could hide most of its own history.

Search is a case-insensitive substring match over the fields that identify a
request: method, URL, and status for traffic captures, and source, method,
route, and source IP for webhooks. The method and status lenses narrow the same
way, so "show me only 4xx" now means every 4xx in the store rather than the ones
that happened to be in the newest page.

The header reports how many results exist beyond the page being shown, so a
filtered list tells you when there is more to find.

### Body search

The traffic tab has an optional **bodies** toggle that extends matching to
request and response content. It is off by default and deliberately bounded: no
index can serve a substring match, so it reads the beginning of every body it
scans. Turn it on when you are looking for a payload value you cannot identify
by URL.

The same filters are available on the interception control API:

```sh
curl 'http://127.0.0.1:9876/local/captures?q=checkout'
curl 'http://127.0.0.1:9876/local/captures?status=5xx'
curl 'http://127.0.0.1:9876/local/webhooks?project=new-project&q=stripe'
```

Both endpoints now also return `total` and `has_more`.

## Sessions that crashed are closed out

An interception session that was killed rather than stopped left its end time
empty forever, so it never showed a duration and stayed ambiguous between
"running" and "abandoned". The next time the app opens, those sessions are
closed out: the end time is backfilled from the session's last captured request,
falling back to its start time when it captured nothing.

They are marked as interrupted rather than silently presented as clean runs, so
you can still tell a crash apart from `wiretap intercept stop`. The sidebar now
shows the capture count for those sessions in the warning color alongside the
marker, instead of hiding the count.

A session owned by a live process is never touched, including during the moment
it is still starting up.

## Relay webhooks are no longer dropped under load

Concurrent webhooks to the same relay could fail with `SQLITE_BUSY` and return
`500`, which meant the sender saw an error and, if it does not retry, the
webhook was lost. Two separate problems caused this: the connection timeout and
foreign-key settings were only applied to the first database connection rather
than all of them, and sequence allocation upgraded a read snapshot to a write,
which SQLite refuses without consulting the timeout at all.

Both are fixed. Concurrent webhooks now queue for the write lock instead of
failing. The same change also fixes foreign keys being unenforced on connections
opened after startup, which could leave orphaned subscriptions and webhooks
behind a deleted project or client.

## Ingress response change

The ingress response is now `200 OK` with `{"status":"received"}`:

```json
{ "status": "received" }
```

It no longer echoes the allocated sequence number. That value is a per-project
counter, so returning it disclosed how many webhooks a project had ever received
to anyone who could POST to the path. The status code is unchanged, so senders
that only check for a 2xx are unaffected; anything parsing `seq` from the body
needs updating.
